1. Đồ án của mình đang làm gì?

Tên đề tài là Adversarial Reinforcement Learning for Test Case Generation: dùng học tăng cường đối kháng để sinh ca kiểm thử. Hệ thống nhận đề bài + một hàm Python cần kiểm tra, dùng Qwen trên máy đề xuất dữ liệu thử và đáp án mong đợi, rồi kiểm chứng test có đúng và làm lộ lỗi hay không.

Câu cần nhớ: mình huấn luyện AI tạo test tốt hơn cho code, bằng phần thưởng thu được từ việc thực thi và kiểm chứng test.

Ví dụ code dùng nhầm công thức tổng từ 1 đến n. Hệ thống phải tìm một n làm lộ lỗi, đồng thời tính đúng đáp án cho n đó. Input khó mà đáp án sai thì test vẫn chưa dùng được.

Hình dung một lớp học: người ra câu kiểm tra là model sinh test; bài làm cần kiểm tra là code; giáo viên chấm theo đáp án là bộ kiểm chứng. Trong vòng đối kháng, một người khác cung cấp những bài làm vẫn sai nhưng qua được các câu hỏi hiện tại, để người ra đề phải nghĩ test khác.

Sản phẩm cuối cùng là gì?

Demo Gradio cho phép chọn bài, xem code, xem test và lý do được chấp nhận/bị loại; có thể sinh bốn test mới bằng model local. Ngoài demo có mã huấn luyện, adapter đã học, bảng so sánh và nhật ký kiểm chứng phương pháp.

Phạm vi hiện tại: tập bài APPS dạng gọi hàm, miền input hữu hạn và phần Python được hỗ trợ. Bản này chưa chấm mọi code người dùng dán vào, chưa phải website thi lập trình hoàn chỉnh hay bản tái lập toàn bộ benchmark bài báo.

Tự kiểm tra: AI sinh test hay AI chấm điểm?

AI học cách sinh test. Bộ chấm chính là chương trình thực thi và đối chiếu reference, không phải chatbot lớn được gọi qua mạng để cho điểm.

2. Đi hết một ví dụ từ đầu đến cuối

Ví dụ tổng từ 1 đến n dùng để học cơ chế, không phải số liệu thực nghiệm APPS.

Đề: tính 1 + 2 + … + n, n nguyên từ 0 đến 8; n = 0 trả 0.

Code cần kiểm tra

def solve(n):
    return n * (n - 1) // 2

Với n = 3, code trả 3 thay vì 6.

Reference: lời giải tham chiếu

def solve(n):
    return n * (n + 1) // 2

Reference chỉ phục vụ bộ chấm, không đưa vào prompt cho model sinh test.

Model nhận đề và code cần kiểm tra, sau đó có thể sinh:

{"input":{"n":3},"expected":6}
BướcThao tácKết quả
1Đọc JSON, kiểm tra hai khóa input/expectedĐọc được
2Kiểm tra n nguyên trong 0–8n = 3 hợp lệ
3Chạy reference với n = 3Đáp án = 6
4So expected model sinh với reference6 = 6, expected đúng
5Chạy code cần kiểm traCode trả 3

Nếu model sinh {"input":{"n":3},"expected":3}, input hợp lệ nhưng expected sai. Không thể lấy code đang bị nghi có lỗi làm chuẩn. Đây là lý do test nhìn hợp lý nhưng không được tính thành công.

Một test gồm input đưa vào và expected mà chương trình đúng phải trả. Giá trị code đang kiểm tra trả về là observed/actual, không tự động là đáp án đúng.

Thử tự chấm một test

Miền n = 0…8; đây chỉ là mô phỏng phép tính, không gọi model và không huấn luyện.

n = 3 → reference = 6, code lỗi = 3. Expected đúng, phát hiện lỗi, reward = 1.

Thử n = 0/expected = 0, rồi n = 3/expected = 3, cuối cùng n = 10. Trong hệ thống thật, cấu trúc JSON và kiểu dữ liệu cũng được kiểm tra, không chỉ hai ô số như mô phỏng.

4. Bản đồ toàn bộ hệ thống

__PIPELINE__
  1. Chuẩn bị dữ liệu: chọn bài APPS, lời giải nguồn, miền input; tạo code lỗi và chia tập theo bài.

  6. Đánh giá: so sánh trên Validation, giữ Test đến khi chốt.

5. APPS là gì, và mình dùng phần nào?

APPS là bộ bài toán lập trình công khai có đề, lời giải và dữ liệu kiểm tra. Introductory là nhóm bài nhập môn. Mình chọn dạng call-based: truyền tham số vào hàm và nhận giá trị trả về; chưa xử lý toàn bộ dạng đọc stdin/in stdout của mọi bài.

Đề và lời giải nguồn lấy từ APPS. Việc chọn bài, giới hạn input, chia tập phát triển và tạo code đột biến là bước chuẩn bị của đồ án. Cách gọi chính xác: “tập con APPS Introductory có code đột biến được kiểm chứng”, không phải toàn bộ APPS hay tập code lỗi do người thi nộp.

Miền nhỏ cho phép đối chiếu hết input đã khai báo. Bài này có 1 + 3 + 9 + 27 + 81 = 121 chuỗi dài 0–4, nhân ba lựa chọn ký tự = 363 input. Hai reference nguồn phải qua test gốc và đồng ý trên miền đó.

Code đột biến được tạo bằng thay đổi cây cú pháp AST, ví dụ == thành !=. Mutant phải khác hành vi reference và không trùng mutant khác. Đã kiểm tra 26.833 cặp code/input cho dữ liệu ban đầu; đó là công việc kiểm chứng, không phải số test model tự nghĩ ra.

6. Train, Validation, Test và bộ chấm

Train giống tài liệu dùng để học; Validation giống bộ bài luyện để chọn phương pháp; Test là bài kiểm tra cuối chưa dùng để sửa cách học. Nếu m1 của một bài nằm ở Train còn m2 cùng đề nằm ở Validation, model có thể hưởng lợi từ việc đã gặp đề. Vì vậy mình chia theo bài, không chỉ xáo trộn dòng code.

Reference cho reward trên Train. Trên Validation, nó chỉ dùng để đánh giá, không có bước cập nhật tham số. Model không được thấy reference hoặc nhân chứng lỗi trong prompt sinh test.

Thứ tự kiểm tra

  1. Đầu ra kết thúc hay bị cắt vì hết token?
  2. Đúng một JSON, không trùng khóa, đủ input/expected?
  3. Input đúng tên tham số, kiểu và miền?
  4. Expected khớp reference, kể cả kiểu/cấu trúc/thứ tự cần thiết?
  5. Code cần kiểm tra trả khác đáp án đúng hoặc gặp lỗi thực thi được hỗ trợ?

true khác "true"; mảng số khác chuỗi mô tả mảng; tên strng khác text. Miền thí nghiệm có thể nhỏ hơn miền đề gốc: số xuất hiện trong ví dụ APPS vẫn có thể bị loại nếu ngoài hợp đồng đang cho phép.

Code chạy qua bộ thông dịch AST giới hạn, không được tùy ý import hay truy cập file/mạng. Lỗi chạm giới hạn bộ kiểm chứng phải dừng lượt để xem xét, không được tính bắt bug. Exception thực thi chương trình được hỗ trợ chỉ tính bắt lỗi khi expected đúng.

Reference là chuẩn trong phạm vi đã xác nhận. Hai lời giải đồng ý và kiểm tra hết miền hữu hạn giúp giảm lỗi, không chứng minh đúng mọi input ngoài miền hay loại trừ lỗi chung.

Dùng đáp án chuẩn để xem input có tiềm năng bắt lỗi là chẩn đoán oracle. Nếu model ghi expected sai, không được sửa bằng oracle rồi tính test đó thành thành tích của model.
